# 고등학생 앞에서 진행하는 Mini Git 시연 매뉴얼

대상은 프로그래밍을 처음 접하는 고등학생입니다. 기본 시연은 약 12~15분이며, 명령을 한 줄씩 입력하면서 설명합니다. 영어 명령을 외우게 하기보다 “기록이 어떻게 연결되는가”를 보여주는 것이 목표입니다.

이 문서의 **입력**은 그대로 복사해 사용하고, **설명 멘트**는 읽거나 자연스럽게 바꿔 말하세요. 긴 ID는 화면에서는 전체를 입력하고 말로는 “1번 기록”처럼 부릅니다.

## 시연 전 준비

1. Python 3.10 이상이 설치된 컴퓨터에서 프로젝트 폴더를 엽니다.
2. 터미널과 이 문서를 나란히 두고, 뒷자리에서도 글자가 보이도록 확대합니다.
3. 아래 순서를 한 번 연습합니다. 인터넷이나 외부 패키지는 필요 없습니다.
4. 본 시연 직전 기존 프로그램에서 `QUIT`을 입력하고 다시 실행합니다. 그래야 문서와 기록 번호가 일치합니다.

터미널에서 실행합니다.

```sh
python main.py
```

Windows에서 `python` 대신 Python Launcher를 쓰는 환경이라면 `py main.py`로 실행합니다.

예상 화면:

```text
Mini Git - type HELP for commands.
mini-git>
```

이제부터 명령은 `mini-git>` 뒤에 입력합니다. 프롬프트 글자 자체는 복사하지 않습니다. 아래 예제는 기존 `examples/demo.txt`와 같은 흐름을 사용합니다. 성공한 COMMIT이나 MERGE를 임의로 추가하면 이후 번호가 달라집니다.

## 1. 관심 끌기 — 약 1분

**설명 멘트**

> “조별 과제 파일을 ‘최종’, ‘진짜 최종’, ‘진짜 진짜 최종’으로 저장한 적 있나요? 나중에는 무엇을 고친 것인지 헷갈리죠. 오늘은 수정 기록에 번호를 붙이고, 어떤 기록에서 이어졌는지 관리하는 프로그램을 보여드리겠습니다.”
>
> “이 프로그램은 실제 파일 내용까지 저장하지는 않습니다. 누가, 언제, 어떤 메모를 남겼고 어떤 기록을 이어받았는지 관리합니다.”

**학생에게 묻기:** “파일 이름만으로 누가 어떤 부분을 바꿨는지 알 수 있을까요?”

두세 명의 답을 듣고 “그래서 수정 이력이 필요합니다”로 연결합니다.

## 2. 준비하고 첫 기록 남기기 — 약 1분

**입력**

```text
INIT "Alice Kim"
COMMIT "Initial commit"
```

**예상 결과**

```text
Initialized repository.
Current branch: main
Current user: Alice Kim
[main 0000000000000001] Initial commit
```

**설명 멘트**

> “INIT은 작업 공간 준비입니다. 작성자는 Alice Kim이고, 기본 작업 흐름의 이름은 main입니다. COMMIT은 기록 한 장을 남기는 명령입니다. Initial commit은 ‘첫 기록’이라는 메모입니다. 긴 번호는 기록을 구별하는 이름이라고 보면 됩니다.”

**화면에서 짚을 부분:** 작성자, main, 끝자리가 1인 ID. 문자열에 공백이 있어 따옴표로 묶었다는 것도 짧게 설명합니다.

## 3. 다른 아이디어를 시도하기 — 약 2분

로그인 기능을 만드는 흐름과 결제 기능을 만드는 흐름으로 나눠 보겠습니다.

**입력**

```text
BRANCH feature
SWITCH feature
COMMIT "Add login feature"
```

**예상 결과**

```text
Created branch: feature
Switched to branch: feature
[feature 0000000000000002] Add login feature
```

**설명 멘트**

> “브랜치는 마지막 기록을 가리키는 이름표입니다. feature라는 이름표를 만든 뒤 그쪽으로 이동했습니다. 이제 로그인 기능을 추가했다는 2번 기록을 남겼습니다. 2번은 1번에서 이어집니다.”

다음으로 기본 흐름에 돌아옵니다.

**입력**

```text
SWITCH main
COMMIT "Add payment feature"
```

**예상 결과**

```text
Switched to branch: main
[main 0000000000000003] Add payment feature
```

**학생에게 묻기:** “3번은 2번을 이어받았을까요, 1번을 이어받았을까요?”

**해설 멘트**

> “정답은 1번입니다. main의 이름표는 아직 1번에 있었기 때문입니다. 지금은 1번에서 로그인 기록 2번과 결제 기록 3번으로 갈라진 상태입니다. 브랜치를 만든다고 기록 전체를 두 벌 복사하는 것은 아닙니다.”

발표자가 기억할 상태: **feature는 2번, main은 3번, 현재 작업 위치는 main**입니다.

## 4. 전체 기록 확인하기 — 약 1분

**입력**

```text
LOG
```

**예상 결과:** 1번, 2번, 3번이 차례대로 나옵니다. 각 줄은 `ID | 작성자 | 시각 | 메시지` 형식입니다. 시각은 실행할 때마다 달라집니다.

**설명 멘트**

> “이 목록은 모든 브랜치의 기록을 보여줍니다. 이 과제에서는 부모 기록이 자식 기록보다 먼저 나오도록 했습니다. 공통 출발점 1번이 먼저 나오고 그 뒤를 이은 2번과 3번이 나옵니다.”
>
> “기록을 점으로 보고 부모 관계를 선으로 보면 그래프가 됩니다. 여기서 그래프는 막대그래프가 아니라 관계를 나타내는 점과 선이라는 뜻입니다.”

알고리즘 이름을 덧붙일 여유가 있으면 “선행 기록부터 처리하는 방식을 위상 정렬이라고 합니다” 정도만 말합니다.

## 5. 두 기록 사이의 길 찾기 — 약 1분

**입력**

```text
PATH 0000000000000002 0000000000000003
```

**예상 결과**

```text
Path: 0000000000000002->0000000000000001->0000000000000003
```

**설명 멘트**

> “2번과 3번은 직접 연결되어 있지 않습니다. 공통 출발점인 1번을 거쳐 가므로 연결선 두 개를 건넙니다. 이 명령은 부모 연결을 양쪽으로 이동할 수 있다고 보고, 가장 적게 건너가는 길을 찾습니다.”
>
> “가까운 곳부터 차례로 확인하는 BFS라는 방법을 썼습니다. 바로 옆을 먼저 보고, 그다음 두 칸 떨어진 곳을 보는 방식입니다.”

## 6. 필요한 기록만 검색하기 — 약 2분

**입력**

```text
SEARCH "login"
```

**예상 결과:** `Found 1 commit(s):`와 함께 2번 `Add login feature`가 나옵니다.

**설명 멘트**

> “로그인이라는 단어로 관련 기록만 찾았습니다. 책 뒤의 찾아보기처럼 단어마다 관련 기록 번호를 미리 모아 둡니다. 이것이 역색인입니다. 검색할 때 모든 기록의 내용을 다시 읽지 않아도 됩니다.”

**입력**

```text
SEARCH "add feature"
SEARCH --author="Alice Kim"
```

**예상 결과:** 첫 검색은 2번과 3번, 작성자 검색은 1번부터 3번까지 나옵니다.

**설명 멘트**

> “단어 두 개를 넣으면 두 단어가 모두 있는 기록을 찾습니다. 문장 순서가 같을 필요는 없습니다. 작성자 이름으로도 찾을 수 있습니다.”

**주의:** 이 검색은 단어 단위입니다. `log`로 `login`을 찾는 부분 검색은 지원하지 않습니다. 소문자와 대문자는 단어 검색에서 같게 처리하지만 작성자 이름은 정확히 입력해야 합니다.

## 7. 날짜와 이름 기준으로 정리하기 — 약 1분

**입력**

```text
LOG --sort-by=date
LOG --sort-by=author
```

**예상 결과:** 이 시연에서는 두 목록 모두 1번, 2번, 3번 순서입니다.

**설명 멘트**

> “날짜순이나 작성자 이름순으로도 볼 수 있습니다. 지금은 한 사람이 차례로 기록해서 화면의 순서가 같습니다. 이름이 같으면 원래 순서를 유지하기 때문입니다.”
>
> “정렬은 카드 묶음을 반씩 나누고 작은 것부터 다시 합치는 병합 정렬을 직접 만들었습니다.”

**발표자 참고:** 이 CLI에는 작성자 변경 명령이 없습니다. 순서를 바꾸려고 INIT을 다시 실행하면 안 됩니다. 서로 다른 작성자의 이름순 정렬은 자동 검사에서 확인합니다. 옵션 정렬에는 기본 LOG의 부모 우선 규칙이 적용되지 않습니다.

## 8. 두 흐름 합치고 조상 확인하기 — 약 2분

현재 main에서 다음을 입력합니다.

```text
MERGE feature
ANCESTORS 0000000000000004
```

**예상 결과:** 병합 메시지는 다음과 같습니다.

```text
[main 0000000000000004] Merge feature into main
```

조상 목록은 **2번, 1번, 3번** 순서로 나옵니다. 자기 자신인 4번은 나오지 않습니다.

**설명 멘트**

> “4번은 로그인 기록 2번과 결제 기록 3번을 함께 부모로 둡니다. 두 흐름을 이어받았다는 뜻입니다. 다만 실제 파일 내용을 합치는 기능은 없고 연결 관계만 만듭니다.”
>
> “ANCESTORS는 조상 기록을 모두 찾습니다. 2번과 3번을 따라가면 양쪽에서 1번을 만나지만 한 번만 출력합니다. 이미 방문한 번호를 적어 두기 때문입니다.”

**학생에게 묻기:** “4번 자신도 조상 목록에 있어야 할까요?”

**답:** 아니요. 자기 자신은 자신의 조상이 아닙니다.

### 시간 여유가 있으면: 길이가 같은 두 경로

```text
PATH 0000000000000001 0000000000000004
```

예상 출력:

```text
Path: 0000000000000001->0000000000000002->0000000000000004
```

> “1번에서 4번으로 가는 길은 2번을 거쳐도, 3번을 거쳐도 두 칸입니다. 같은 길이일 때에는 번호 문자열의 사전순으로 먼저 오는 길을 고르도록 규칙을 정했습니다.”

## 9. 마무리 — 약 1분

**설명 멘트**

> “오늘은 기록을 남기고, 서로 다른 흐름으로 나누고, 검색하고, 다시 연결해 봤습니다. 커밋은 기록 한 장, 브랜치는 이름표입니다. 가까운 기록부터 길을 찾거나, 조상을 따라가거나, 찾아보기로 검색하는 일이 모두 자료구조와 알고리즘의 활용입니다.”
>
> “이 프로그램은 학습용이라 파일 내용은 저장하지 않고, 종료하면 기록도 사라집니다. 실제 Git은 파일 내용과 이력을 계속 보관하는 등 더 많은 일을 합니다.”

**입력**

```text
QUIT
```

`Bye!`가 표시되면 종료입니다. 더 자세한 원리 설명은 [학습 자료](LEARNING.md)를 활용하세요.

## 5분으로 줄여야 할 때

1. “최종 파일” 비유로 시작합니다.
2. 2~3단계로 기록 세 개와 두 브랜치를 만듭니다.
3. `LOG`로 전체 기록을 보고, `SEARCH "login"`으로 검색합니다.
4. `MERGE feature`로 합친 뒤 `ANCESTORS 0000000000000004`로 연결 관계를 확인합니다.
5. 파일 내용은 저장하지 않는 학습용 프로그램이라고 설명하고 종료합니다.

정렬과 PATH 설명을 생략하면 핵심 흐름을 짧게 보여줄 수 있습니다. 커밋을 만드는 단계는 생략하지 않아야 번호가 유지됩니다.

## 시연 중 문제가 생겼을 때

- **`Invalid args`**: 인자 개수와 큰따옴표를 확인합니다. 예를 들어 `COMMIT "Add login feature"`처럼 메시지를 묶습니다. 문서의 곧은 큰따옴표를 그대로 사용하세요.
- **`Unknown branch: ...`**: main과 feature의 철자 및 대소문자를 확인합니다. BRANCH를 실행했는지도 확인합니다.
- **`Unknown commit: ...`**: `LOG`로 실제 ID를 확인하고 전체 번호를 복사합니다. 임의로 커밋을 추가했다면 문서의 번호와 달라질 수 있습니다.
- **`Already initialized`**: INIT으로 재시작할 수 없습니다. `QUIT` 후 터미널에서 `python main.py`로 다시 시작합니다.
- **`Repository not initialized`**: 새 실행에서 INIT을 빠뜨린 것입니다. 2단계부터 진행합니다.
- **`Merge requires two distinct non-empty heads`**: 두 브랜치에 서로 다른 마지막 기록이 필요합니다. 이 문서의 분기·커밋 순서를 확인합니다.
- **검색 결과가 0개**: `login` 철자를 확인합니다. 단어 일부만 입력했거나 구두점을 붙이면 다른 토큰입니다.
- **기록 번호나 순서가 헷갈림**: 가장 간단한 복구는 종료 후 2단계부터 다시 진행하는 것입니다. 성공한 COMMIT과 MERGE만 번호를 증가시킵니다.
- **`main.py`를 찾을 수 없음**: 프로젝트 폴더에서 터미널을 열었는지 확인합니다. 프로그램 밖 터미널에서 실행해야 합니다.

오류 시 이렇게 말하면 자연스럽습니다.

> “프로그램이 어떤 입력을 이해하지 못했는지 알려주고 있네요. 안내에 맞게 고쳐 보겠습니다. 이런 잘못된 입력도 처리하는 것이 프로그램 기능의 일부입니다.”

## 학생이 물어볼 만한 질문

**“이걸 쓰면 내 파일도 복구할 수 있나요?”**

이번 프로그램은 메모와 연결만 저장하므로 할 수 없습니다. 실제 Git은 커밋에 담긴 파일 내용을 활용할 수 있다는 차이가 있습니다.

**“번호가 길면 암호인가요?”**

아닙니다. 여기서는 증가 번호를 16진수로 표시한 식별자입니다. 실제 Git의 내용 기반 해시와는 다릅니다.

**“왜 부모가 둘이에요?”**

두 갈래의 작업을 이어받았다는 사실을 남기기 위해서입니다. 일반 커밋은 부모 하나, 병합 커밋은 이 시연에서 둘입니다.

**“그래프에 고리가 생기지는 않나요?”**

새 기록이 이미 존재하는 기록만 부모로 삼고 기존 부모 연결을 바꾸지 않으므로, 부모 방향으로 계속 따라가서 자기 자신으로 돌아올 수 없습니다. 이런 구조를 DAG라고 부릅니다.

**“검색하면 항상 바로 나오나요?”**

찾아보기 덕분에 필요 없는 기록을 덜 보지만, 검색 결과가 많으면 읽고 출력하는 시간도 필요합니다.

## 발표 직전 마지막 확인

- 새 실행에서 시작했는가?
- 화면 글자가 충분히 큰가?
- BRANCH와 SWITCH의 차이를 설명할 수 있는가?
- 2번과 3번의 부모가 모두 1번임을 설명할 수 있는가?
