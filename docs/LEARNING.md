# 비전공자를 위한 Mini Git 학습 자료

## 1. 이 문제를 일상 언어로 바꾸면

보고서를 작성하면서 `최종`, `진짜최종`, `최종수정` 파일을 만들어 본 적이 있나요? 어느 것이 어떤 파일을 고친 것인지 헷갈릴 수 있습니다. 이 문제는 수정 이력에 번호를 붙이고, **어느 기록에서 이어졌는지 연결해 관리하자**는 문제입니다.

이번 프로그램은 보고서 원문을 복사하지 않습니다. “이지은이 오후 3시에 서론 수정이라는 기록을 남겼고, 그 직전 기록은 1번이다”라는 정보만 저장합니다. 실제 Git의 일부 원리를 작게 재현합니다.

먼저 다음 문장을 설명할 수 있으면 출발점은 충분합니다.

> 커밋은 기록 한 장이고, 브랜치는 마지막 기록을 가리키는 이름표이며, HEAD는 지금 작업 중인 브랜치를 가리킨다.

## 2. 실행 화면 읽기

터미널은 글자로 명령을 주고받는 창입니다. 이 폴더에서 `python main.py`를 실행하면 `mini-git>`가 나옵니다. 이것은 “다음 명령을 입력하세요”라는 표시입니다. 명령을 입력할 때 `mini-git>` 자체는 적지 않습니다.

```text
INIT "이지은"
COMMIT "서론 작성"
COMMIT "결론 작성"
LOG
```

`INIT`은 준비, `COMMIT`은 기록 추가, `LOG`는 기록 목록 보기입니다. 출력의 긴 번호는 기록을 구별하는 ID입니다. `author`는 작성자, `timestamp`는 기록 시각, `message`는 메모입니다. 시각 끝의 `+00:00`은 UTC이며 한국 시각은 여기서 9시간을 더합니다.

공백은 인자를 나누는 경계입니다. `COMMIT 서론 작성`은 인자가 둘이라 거절됩니다. `COMMIT "서론 작성"`은 인자 하나로 읽힙니다. 따옴표는 메모의 글자가 아니라 묶음 표시입니다.

## 3. 자료구조란 무엇인가

자료구조는 정보를 정리하는 방식입니다. 옷을 옷걸이에 걸지, 서랍에 접어 넣을지 정하는 것과 비슷합니다. 정리 방식에 따라 찾기와 추가하기가 쉬워집니다.

이 프로그램의 `list`는 순서가 있는 목록, `dict`는 이름으로 값을 찾는 주소록, `set`은 중복을 없애는 모음입니다. `deque`는 앞에서 꺼내고 뒤에 넣기 편한 대기 줄입니다.

`commits[번호]`를 보면 번호에 해당하는 기록을 바로 가져옵니다. 이 주소록 덕분에 매번 전체 기록을 처음부터 읽을 필요가 없습니다. 딕셔너리 조회는 보통 평균 O(1)이지만, 모든 상황에서 무조건 같은 시간이 걸린다는 뜻은 아닙니다.

커밋에는 `parents`도 들어 있습니다. 이것이 이전 기록들의 번호 목록입니다. 첫 기록은 부모 0개, 일반 기록은 1개, 이번 MERGE로 만든 기록은 2개입니다. 데이터 표현과 탐색 알고리즘은 2개보다 많은 부모도 다룰 수 있습니다.

## 4. 브랜치를 손으로 따라가기

새 실행에서 아래 명령을 차례대로 입력합니다. 설명에서는 긴 ID 대신 1, 2, 3이라고 부르겠습니다.

```text
INIT "이지은"
COMMIT "초안 작성"
BRANCH experiment
COMMIT "정식 결론 작성"
SWITCH experiment
COMMIT "다른 결론 작성"
LOG
```

첫 커밋 1을 만들면 main이 1을 가리킵니다. experiment를 만들면 두 이름표가 모두 1을 가리킵니다. main에서 2를 만들면 main만 2로 움직입니다. experiment로 바꾼 후 3을 만들면 3의 부모는 2가 아니라 1입니다.

따라서 부모 관계는 “2의 부모는 1, 3의 부모도 1”입니다. 파일 폴더 두 벌을 복사한 것이 아니라 같은 출발 기록에 서로 다른 후속 기록을 붙인 것입니다.

확인 질문: `BRANCH experiment` 직후 현재 브랜치는 무엇일까요? **main입니다.** 생성과 전환은 별개입니다.

## 5. 그래프와 DAG

그래프는 점과 연결선으로 관계를 표현한 자료구조입니다. 여기서는 커밋이 점이고 부모 관계가 선입니다. 수학 문제의 함수 그래프와는 다른 뜻입니다.

저장된 부모 화살표는 새 기록에서 옛 기록을 향합니다. 새 커밋은 이미 존재하는 커밋만 부모로 삼고, 기존 커밋의 부모는 바꾸지 않습니다. 따라서 부모를 계속 따라가다가 자기 자신으로 돌아올 수 없습니다.

이처럼 방향이 있고 빙글 돌아 제자리로 오는 고리가 없는 그래프를 DAG라고 부릅니다. “방향성 비순환 그래프”를 줄인 말입니다. 병합으로 부모가 둘이 될 수 있으므로 항상 단순한 나무 구조인 것은 아닙니다.

주의할 점: PATH에서는 이동 편의를 위해 같은 연결을 양방향으로 취급합니다. 이것은 경로 계산 규칙이며, 저장된 부모 관계가 무방향이라는 뜻은 아닙니다.

## 6. 부모가 먼저 나오는 LOG

수업을 듣기 전에 선수 과목을 끝내야 한다고 생각해 보세요. 아직 끝나지 않은 선수 과목 수를 적고, 그 수가 0인 과목부터 처리합니다.

프로그램도 커밋마다 아직 출력하지 않은 부모 수를 셉니다. 부모 0개인 커밋을 대기 줄에 넣습니다. 하나를 출력하면 그 자식들의 남은 부모 수를 1씩 줄입니다. 0이 된 자식은 대기 줄 뒤에 넣습니다.

이것이 Kahn 방식의 위상 정렬입니다. 부모 포인터 방향과 별개로 **출력에서는 부모가 자식보다 먼저**라는 제약을 적용합니다. 날짜만 정렬하는 것과 다릅니다. 시계 정보가 이상해도 부모 관계만 올바르면 부모 우선 순서를 지킵니다.

`LOG --sort-by=author`는 다른 목적의 명령입니다. 작성자 이름순을 우선하므로 부모가 먼저라는 약속은 적용하지 않습니다.

## 7. PATH: 가장 적게 건너가는 길

앞 실습의 2에서 3으로 가려면 2, 1, 3 순서로 이동합니다. 연결선 두 개를 건넙니다. 여기서 최단은 시간이 짧다는 뜻이 아니라 **건너는 선의 개수가 가장 적다**는 뜻입니다.

BFS는 가까운 곳부터 탐색합니다. 출발점에서 한 번에 가는 곳을 먼저 보고, 두 번에 가는 곳, 세 번에 가는 곳을 차례로 봅니다. 대기 줄을 사용하기 때문에 먼저 발견한 곳부터 처리합니다. 방문할 때 어디에서 왔는지 적어 두면 도착 후 길을 거꾸로 복원할 수 있습니다.

```text
PATH 0000000000000002 0000000000000003
```

예상 출력은 `Path: 0000000000000002->0000000000000001->0000000000000003`입니다.

이제 experiment에 있는 상태에서 `MERGE main`을 입력하면 4의 부모는 3과 2입니다. 1에서 4로 가는 최단 경로는 1→2→4와 1→3→4 두 가지입니다. 프로그램은 이웃 ID를 사전순으로 정렬해서 BFS를 수행하므로 1→2→4를 선택합니다. 같은 길이의 경로들이 앞부분부터 사전순으로 탐색되며, 처음 방문한 경로를 보존하기 때문입니다. ID는 구분자 `->`를 포함하지 않는 16진수 문자열이어서 이 비교가 경로 문자열 기준과 맞습니다.

연결이 끊어진 예도 직접 만들 수 있습니다. 새 실행에서 커밋을 만들기 전에 빈 브랜치 `other`를 만들고, main과 other에서 각각 첫 커밋을 만드세요. 두 기록 사이에는 부모 연결이 없어 PATH가 `No path`를 출력합니다.

## 8. ANCESTORS: 모든 조상 찾기

가계도에서 부모, 조부모, 그 위를 차례로 확인하는 것과 비슷합니다. DFS는 한 방향으로 먼저 깊이 들어갑니다. 이번 코드는 나중에 볼 번호를 스택에 쌓습니다. 스택은 접시 더미처럼 마지막에 넣은 것을 먼저 꺼냅니다.

병합 커밋 4에서 부모 2와 3을 따라가면 양쪽 모두 1에 도착합니다. 방문한 번호를 집합에 적어 두면 1을 두 번 출력하지 않습니다. 시작점 4 자신은 조상이 아니므로 제외합니다.

```text
ANCESTORS 0000000000000004
```

2, 3, 1이 각각 한 번씩 나오는지 확인하세요. 출력 순서는 DFS 방문 순서이며 번호순일 필요는 없습니다. 재귀 호출 대신 반복문을 써서 기록이 길어져도 Python의 재귀 깊이 제한에 걸리지 않습니다.

## 9. 역색인: 책 뒤의 찾아보기

책에서 “민주주의”라는 단어를 찾을 때 모든 페이지를 읽는 대신 찾아보기에서 페이지 번호를 확인합니다. 역색인도 같은 원리입니다.

메시지가 `Add login feature`이면 `add`, `login`, `feature` 각각의 목록에 그 커밋 번호를 추가합니다. 같은 메시지에서 단어가 반복되어도 번호는 한 번만 넣습니다. 작성자 이름별 목록도 따로 만듭니다.

`SEARCH "LOGIN"`은 `login` 목록만 꺼냅니다. `SEARCH "login feature"`는 두 목록에 공통으로 있는 번호를 찾습니다. 문장이 그대로 연속해서 있어야 하는 검색은 아닙니다. 구두점을 제거하지 않으므로 `login,`과 `login`은 다른 단어입니다.

한 단어 검색은 평균적으로 목록 찾기 O(1)에 결과 k개를 읽는 O(k)가 더해집니다. 모든 기록을 읽는 O(N)보다 유리할 수 있습니다. 다만 그 단어가 모든 기록에 있으면 결과 자체가 N개라 O(N)이 필요합니다. 빠른 검색 대신 인덱스를 저장할 메모리와 커밋 생성 시 갱신 작업이 추가됩니다.

여러 단어는 단어 수를 q, 조회한 목록 길이의 합을 P라 할 때 목록 길이 정렬과 교집합 처리에 대략 O(q log q + P), 출력에 O(k)가 필요합니다. 이는 문자열 처리 비용을 별도로 본 평균적인 집합 연산 기준입니다.

## 10. 직접 만든 병합 정렬

숫자 카드 4, 1, 3, 2를 정리한다고 합시다. 먼저 반씩 나눠 4, 1과 3, 2로 만듭니다. 다시 나누면 한 장씩 남습니다. 한 장은 이미 정렬되어 있습니다. 작은 카드부터 합치면 1, 4와 2, 3이 되고, 다시 합치면 1, 2, 3, 4입니다.

이 방법이 병합 정렬입니다. 프로그램의 `key`는 카드에서 무엇을 비교할지 정하는 규칙입니다. 날짜 정렬에서는 시각을, 작성자 정렬에서는 이름을 꺼냅니다.

값이 같을 때 왼쪽 묶음의 원소를 먼저 꺼내므로 원래 순서를 유지합니다. 이것을 **안정 정렬**이라고 합니다. 같은 작성자 커밋끼리는 먼저 생성된 것이 앞에 남습니다.

O 표기는 입력이 많아질 때 작업량이 어떻게 커지는지를 말합니다. 정확한 초 단위 시간이 아닙니다. N을 1,024개라고 하면 반으로 약 10번 나눌 수 있습니다. 각 단계에서 전체 카드 규모의 일을 하므로 O(N log N)입니다. 평균과 최악 모두 O(N log N)이며 별도의 목록을 쓰므로 최대 추가 공간은 O(N)입니다.

기본 LOG의 위상 정렬과 병합 정렬은 이름에 모두 ‘정렬’이 있지만 다릅니다. 전자는 선후 관계를 지키고, 후자는 날짜나 이름의 크기를 비교합니다.

## 11. 주요 알고리즘의 비용을 말로 설명하기

V는 커밋 수, E는 부모 연결 수, d(v)는 한 커밋에 연결된 이웃 수입니다. ID 비교 비용은 간단히 일정하다고 가정합니다.

- 기본 LOG: O(V + E). 각 커밋과 연결을 한 번씩 확인합니다. 작업 공간 O(V).
- ANCESTORS: 방문 가능한 조상과 연결에 비례합니다. 최악 O(V + E). 스택과 방문 집합 공간은 최악 O(V + E).
- PATH: BFS 자체는 O(V + E)이지만 이 구현은 동률 규칙을 위해 이웃 정렬도 합니다. 최악 O(V + E + Σ d(v) log d(v))이며 추가 작업 공간은 O(V + 최대 이웃 수)입니다.
- 날짜/작성자 LOG: 병합 정렬 시간 O(V log V), 추가 공간 O(V).
- 저장 공간: 커밋과 그래프에 O(V + E), 여기에 메시지 원문과 역색인 목록 저장 비용이 더해집니다.

즉, PATH를 설명할 때 “BFS니까 무조건 전체 O(V + E)”라고만 말하면 이 프로그램의 이웃 정렬 비용을 빠뜨리게 됩니다.

## 12. 코드를 읽는 순서

1. `main.py`: 프로그램이 어디서 시작하는지 봅니다.
2. `mini_git/cli.py`의 `repl`: 입력→해석→실행→출력의 반복을 봅니다.
3. 같은 파일의 `execute`: 따옴표를 해석하고 명령별 기능을 호출하는 부분을 봅니다.
4. `mini_git/repository.py`의 `Commit`과 `commit`: 기록 한 장의 모양과 연결·인덱스 갱신을 봅니다.
5. `mini_git/algorithms.py`: 앞서 손으로 따라간 BFS, DFS, 정렬을 코드와 연결합니다.
6. `tests/test_mini_git.py`: 어떤 입력에 어떤 결과가 맞다고 확인하는지 봅니다.

`def`는 기능 정의, `return`은 결과 돌려주기, `if`는 조건 판단, `for`는 반복입니다. `class`는 관련 정보와 기능을 묶는 틀입니다. `raise ValueError`는 잘못된 요청을 알려주는 신호이고, CLI가 받아 읽을 수 있는 오류 문장으로 보여줍니다.

## 13. 자주 생기는 오해

- COMMIT을 했다고 내 보고서 파일이 저장되는 것은 아닙니다. 이번 과제는 메타데이터만 다룹니다.
- 긴 ID를 쓴다고 암호화한 것은 아닙니다. 이번 ID는 중복 없는 증가 번호입니다. 실제 Git의 해시는 내용으로 계산한다는 차이가 있습니다.
- SWITCH는 작성자 변경 명령이 아닙니다. 한 실행에서는 INIT의 사용자가 계속 기록합니다. 이름순 정렬의 차이는 테스트에서 작성자를 달리한 데이터로 검증합니다.
- 부모가 두 개여도 사이클은 아닙니다. 방향을 따라 출발점으로 돌아올 수 있어야 사이클입니다.
- 종료 후 기록이 없어지는 것은 이 과제에서 허용한 메모리 저장 방식의 결과입니다.

## 14. 이해 확인 문제와 해설

1. 브랜치를 만들면 기존 커밋이 복제되나요? 아니요. 같은 커밋 ID를 가리키는 이름표가 추가됩니다.
2. 두 브랜치의 마지막 기록 사이를 왜 부모 방향만 따라가면 안 되나요? 과제 PATH는 양방향 이동을 허용하므로 부모에서 다른 자식으로도 갈 수 있어야 합니다.
3. 병합 뒤 조상을 검색할 때 방문 집합이 필요한 이유는? 두 부모를 통해 같은 조상에 도착할 수 있어 중복 처리와 출력을 막아야 하기 때문입니다.
4. 작성자 정렬은 항상 부모 우선인가요? 아니요. 이름 비교와 부모 선후 관계는 다른 조건입니다.
5. 역색인 검색은 언제나 O(1)인가요? 아니요. 결과 목록을 읽고 출력하는 비용도 있습니다.
6. 이 프로그램의 커밋 그래프에 고리가 생기지 않는 이유는? 새 기록이 이미 존재하는 기록만 부모로 삼고 기존 부모 정보를 바꾸지 않기 때문입니다.

## 15. 다른 사람에게 설명하는 1분 발표 예시

“저는 수정 이력을 관리하는 작은 프로그램을 만들었습니다. 기록마다 번호, 작성자, 시각, 메시지와 이전 기록 번호를 저장합니다. 브랜치는 마지막 기록을 가리키는 이름표입니다. 새 기록은 기존 기록만 부모로 연결하기 때문에 과거를 따라가다 자기 자신으로 돌아오는 고리가 없습니다. 전체 목록은 부모부터 출력하고, 두 기록 사이의 가장 짧은 길은 가까운 곳부터 찾습니다. 모든 조상은 부모 방향으로 깊이 따라갑니다. 검색은 책의 찾아보기처럼 단어별 번호 목록을 미리 만들어 빠르게 처리합니다. 날짜와 이름 정렬은 반씩 나눠 합치는 병합 정렬을 직접 구현했습니다. 실제 파일 저장과 네트워크 기능은 없는 학습용 프로그램입니다.”

## 16. 원문의 80시간을 활용하는 학습 계획

- 1~10시간: 실행, 기본 Python 문법, 커밋 필드 이해.
- 11~24시간: 브랜치 실습과 딕셔너리·목록·집합 이해.
- 25~38시간: DAG와 기본 LOG를 종이에 따라 그리기.
- 39~50시간: BFS·DFS, 연결 끊김과 병합 경로 실습.
- 51~62시간: 역색인과 병합 정렬을 작은 입력으로 따라가기.
- 63~72시간: 테스트 실행, 잘못된 입력 추가, 오류 원인 설명.
- 73~80시간: README를 보며 새 환경에서 실행하고 GitHub 업로드 연습 및 발표.

시간은 권장 배분입니다. 각 단계에서 코드를 외우기보다 “이 입력을 주면 무엇이 왜 나오는가”를 설명하는 것을 목표로 하세요.
